Impressão & Validação de NF-e

Dois módulos que eu criei e mantenho: o operador bipa um protocolo, uma guia ou uma doca, imprime as notas fiscais do lote e depois valida cada nota bipando a chave de acesso.

  • Arquitetura VIPER flat (entity · interactor · presenter · view · router · store · service), com o interactor retornando Result<T> em vez de lançar exceção para fluxo esperado.
  • Migração dos dois módulos para o envelope Result<T> do backend .NET, decidindo o fluxo pelo código do erro (bloqueio de negócio vira aviso; falha HTTP vira erro).
  • Entrada por doca com lista de lotes, identificação de redespacho e cache de “validado” por lote; trava contra bipe duplicado enquanto a requisição está em andamento.
  • Leitura de códigos de barras centralizada em um parser compartilhado entre os módulos, com contribuição própria no pacote.
  • Contrato de API negociado com o time de back antes da integração, com mock local atrás de flag para não ficar bloqueado.

Orquestrador de contexto para agentes de IA

Toda sessão nova de IA num módulo começava do zero: sem a arquitetura, sem os padrões que já tinham causado bug, sem saber que o problema já tinha sido resolvido em outro módulo. Projetei um repositório que resolve isso com uma linha de configuração.

  • Um único CLAUDE.md importado via @import por qualquer módulo: um git pull atualiza o contexto de todos os consumidores, sem cópia.
  • 14 seções de padrões, cada uma com o bug real que a violação causou, e uma tabela de regras absolutas que o agente recusa violar, explicando o porquê e oferecendo o caminho correto.
  • 14 skills: roteador, fluxo completo (análise → desenvolvimento → testes → revisão) e uma skill por camada VIPER.
  • Log de decisões por atividade (Decisão → Por quê → Alternativa): 7 atividades, 94 decisões. Decisões pontuais viram regra geral com o tempo.
  • Onboarding de perfil pessoal que vive fora do repositório (preferências de um dev nunca vazam para outro) e governança de merge com aprovadores definidos.
  • Checklist “antes de confiar”: conferir tag publicada, branch e dependência antes de afirmar que algo está no ar.

APIs REST em .NET — CQRS sobre Oracle

Endpoints e features completas no back-end do app. A primeira delas, o Registro de Ocorrências, foi uma prova de conceito full-stack feita ainda como QA. A aprovação dela oficializou minha transição para desenvolvimento.

  • Registro de Ocorrências, de ponta a ponta: command e query com handlers MediatR, validators FluentValidation, mapeamentos AutoMapper, controller versionado, repositório Oracle e testes xUnit dos handlers.
  • SQL sempre parametrizado (bind variables do Oracle, nunca interpolação), com tratamento estruturado de exceções no repositório e fuso horário explícito na gravação.
  • Endpoint de detalhes de produto por código de barras e ajustes na validação de endereço usada na conferência.
  • APIs REST versionadas (/api/v1), documentadas em OpenAPI/Swagger, com respostas padronizadas e erros de validação claros para quem consome.
  • No mobile da mesma feature: fila offline com sincronização automática e persistência em MMKV.
  • Nas features de NF-e, desenho do contrato de API junto com o time de back antes da integração, até o envelope Result<T> e os códigos de erro.

Bugs reais que viraram regra

O olhar de QA continua: quando algo quebra, investigo até a causa, corrijo e documento para que ninguém caia no mesmo problema.

Motor SQL que agregava linha a linha

Sintoma
No Professor SQL, SELECT AVG(salario), MAX(salario) FROM funcionarios devolvia 15 linhas iguais e deixava um desafio impossível de concluir.
Causa
O motor original interpretava SQL com expressões regulares. Sem árvore sintática, agregação sem GROUP BY era calculada por linha.
Correção
Motor reescrito com tokenizer e parser descendente recursivo; agregação sem grupo vira um grupo único.
Regra
Cada desafio ganhou uma solução de referência testada: 161 testes no total.

Singleton que deixava de ser singleton

Achado
Em uma auditoria de módulo contra os padrões, a biblioteca compartilhada estava como eager: true, herdada do commit de scaffold.
Risco
O módulo resolve a própria cópia antes da negociação do Module Federation. Os Providers do shell deixam de ser os mesmos, e useAuth() pode voltar null sem nenhum erro de build.
Correção
singleton: true, eager: false, conferido nos outros 7 módulos com um script de varredura.
Regra
Virou regra absoluta no orquestrador e item do checklist de revisão.

Campo opcional que derrubava a tela

Sintoma
O backend respondia certo (200, succeeded: true), mas o app mostrava um diálogo de erro genérico.
Causa
O .NET serializa campo ausente como null explícito, e o schema Zod do envelope usava .optional(). O parse falhava antes de o presenter olhar a resposta.
Correção
.nullish() nos campos do envelope e .parse() sempre dentro do try/catch da chamada, para nunca vazar erro técnico ao operador.
Regra
Duas regras novas nos padrões do time, aplicadas a todos os módulos.
